# ADR-0009: Two-layer error correction — RaptorQ across frames, Reed-Solomon within frames

**Status:** Accepted · **Date:** 2026-10-09 · **Pairs with:** spec §7.5, test suite `fec/`

## Context

The optical channel fails in two different ways: some frames are missed entirely (camera and display out of phase, the user's hand moves, a person walks past), and captured frames contain scattered symbol errors (blur, glare, color misclassification). The Broadcast mode has no back channel at all, so the sender cannot retransmit on request.

## Decision

**Outer code — RaptorQ (RFC 6330)** across frames:

- Source block = up to 8 Envelope segments (≤ 8 MiB), so large files decode progressively and memory stays bounded.
- Symbol size T is fixed per tier so one frame carries exactly one encoding symbol plus header.
- The sender streams source symbols first, then repair symbols indefinitely, cycling across source blocks. A receiver recovers a block from any K′ received symbols with failure probability below 10^-6 at K′ + 2.
- Encoding Symbol IDs and source block numbers travel in the frame header.

**Inner code — Reed-Solomon over GF(2^8)**, applied per frame:

- RS(255, 207) codewords (code rate ≈ 0.81, corrects 24 symbol errors per codeword), interleaved so that adjacent cells belong to different codewords. A local defect such as a glare spot spreads across many codewords instead of overwhelming one.
- A frame whose RS decode fails in any codeword is discarded as an erasure; RaptorQ absorbs it.
- The 12-byte frame header uses a separate, stronger code (RS(20, 12), correcting 4 byte errors) at 1 bit per cell in black and white, written twice (top and bottom strips), so headers survive even when data does not. That is what drives the live progress display.

Implementation: Rust `raptorq` crate (Apache-2.0), cross-checked for bit-exact symbol output against an independent RFC 6330 implementation, and `reed-solomon-erasure`/custom GF(256) for the inner code, with GPU-side syndrome computation (ADR-0011).

## Alternatives considered

- **LT codes.** Simpler, but higher reception overhead (typically 5–10%) than RaptorQ's near-zero. Rejected.
- **Wirehair** (as used by libcimbar). Excellent performance, BSD-licensed, but no IETF specification; RaptorQ's RFC matters to government reviewers. Rejected in favor of the standard.
- **LDPC inner code.** Better at soft decoding; adds complexity before data shows it is needed. Revisit after M1 if RS is the bottleneck.

## Consequences

- Broadcast receivers can join mid-stream and still finish, because any K′ symbols suffice.
- Overhead budget: inner ≈ 19%, outer ≈ 0.1–2% reception overhead, header ≈ 3% of cells.

## Verification

- `fec/raptorq.conformance`: encoding symbols generated by `raptorq` match an independent RFC 6330 implementation for 1,000 random (K, T, ESI) cases.
- `fec/erasure.sweep`: decode success vs. frame-loss rate 0–60% across 10,000 random seeds; success ≥ 99.9999% at K′ + 2 received.
- `fec/burst`: synthetic glare blobs covering up to 8% of a frame are corrected by the interleaved inner code.
